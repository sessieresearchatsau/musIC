# Concatenation examples

Sets paired with their indexed concatenation (IC) form, recorded verbatim as
given. These are the reference cases for working out how a set gets reduced,
and later for testing a reducer: each IC form must expand back to its set
exactly.

Notes on patterns and the reduction process go in the last section, kept
separate from the raw examples.

## Observed patterns

Based on examples 2, 3 and 4, which all come from `ReduceSetList`. Example 1 is
left out until the set that matches it is available.

The source of `ReduceSetList` is in
[`2026/reference/SSSiCv102.wl`](../../reference/SSSiCv102.wl) (lines 633–920).
Running it with `wolframscript` on the three stored sets gives exactly the
concatenations recorded above, with the same index names. Each output also
expands back to its input exactly. Tracing the intermediate steps of examples 2
and 3 confirmed the steps described below.

### What the output is made of

Every result is a flat list mixing three kinds of item:

| Kind | Form | Examples |
|---|---|---|
| Literal | an element copied as is | `{1}`, `{1, 2}`, `{3, 4}`, `{42, 43}`, `{255, 256, 257}` |
| Run | `IndexedConcatenate[x…, n]` (`€ⁿ[…]`): a fixed sequence repeated `n` times, no index | `€²[{29}]`, `€²²⁰[{257}]` |
| Indexed block | `IndexedConcatenate[body…, {i, 1, N}]`: a body evaluated for i = 1…N and joined | the large blocks in all three examples |

A body is again a sequence of literals, runs and indexed blocks, and its
entries may depend on the enclosing index. That is how the nesting arises.

### The algorithm

`ReduceSetList[l]` tries the steps below in order. As soon as one changes the
list, it calls `improveReduction` and then calls itself again on the result. A
step only runs once every earlier step has stopped finding anything.

**Step 1: exact runs of one element.** Any element repeated 2 or more times in
a row becomes `IndexedConcatenate[a, count]` (lines 831–833).

**Step 2: exact runs of longer blocks.** For block lengths 2, 3, … up to half
the list, it looks for a block of that length that repeats exactly, back to
back, and replaces it with `IndexedConcatenate[block…, count]` (lines 845–863).
None of the three examples contains this case.

**Step 3: generic patterns, the source of the indexed blocks** (lines 877–917).

1. *Build a skeleton.* Every integer except 1 is replaced by 0:
   `gl0 = l0 /. (i_Integer /; i != 1) -> 0`. So `{4, 5}` and `{17, 18}` look
   the same, but **1 is kept as a structural value**. That is why markers like
   `{1}`, `{1, 1}` and `{1, 1, 2}` line up across periods. The skeleton also
   covers runs made earlier: `€⁵[{1, 8}]` becomes `€⁰[{1, 0}]`, so runs of
   different lengths still match.
2. *Find the shortest repeating skeleton.* Starting at body length 1 and going
   up, it looks for the first length at which some stretch of the skeleton
   repeats 2 or more times, with matches not allowed to overlap.
   `SequencePosition` finds every such stretch at that length, scanning from
   the left.
3. *Choose an index name.* This is the first of `n$1`, `n$2`, … that doesn't
   already occur in the list (lines 904–907). Every stretch found in this pass
   gets the same name.
4. *Fit the numbers* (`FindSeqFns`, lines 638–658). The stretch is split into
   periods of the body length. The integers in each period are read off in
   order, including the repeat counts inside runs, and each position across
   the periods is passed to Mathematica's built-in `FindSequenceFunction`. The
   resulting formulas replace the integers of the first period, and the
   iterator is always `{n$i, 1, number of periods}`.
5. *Verify.* The candidate is kept only if `ExpandAll` of it equals the
   original stretch. Otherwise the stretch is left as it was.

The step runs again until the list stops changing. The body length is not
reset between passes, so passes run in order of increasing body length.

**`improveReduction`: rolling** (lines 659–818). This step runs after every
change, once for each indexed block. Its job is to grow a block, since step 3
only finds periods whose skeletons are identical.

- *Roll left.* The last item of the body moves to the front, with `i → i − 1`
  substituted into it. The block then takes in the items to its left that the
  moved item now accounts for. This repeats until the expanded list would
  change.
- *Adjust the range.* Each full cycle of rolls (as many rolls as the body has
  items) adds one to the upper limit of the index. The start always stays 1.
- *Extend right.* It then tries to absorb whole periods on the right, and merges
  neighbouring runs of the same element.

A comment in the source says this is meant to "pick up cases like €⁰[___],
which can't be identified otherwise."

### How the patterns in the examples arise

**Run counts become formulas.** Step 3 fits every integer, including the count
of a run, so the count turns into a formula in the outer index: `k − 1` (ex. 2),
`k + 1` (ex. 3), `2^k + 1` (ex. 4).

**A count of 0 or 1 comes from rolling, not from matching.** In example 2, the
generic match found only 25 periods. It started at `{1, 2, 4}`, partway through
a period, because the first periods have run counts of 0 and 1. A count of 0
means the run is absent, and a count of 1 means a bare element rather than a
run, so those periods have a different skeleton. Rolling then moved the block
left over those periods, giving `k = 1…27`. That is why the k = 1 period
contains `€⁰[{1, 1, 3}]`.

**Which formulas are possible** depends on `FindSequenceFunction`, not on a
fixed list. It found constants, steps of ±1 and `2^k` here, and it can return
other polynomials, exponentials and recurrences. A port needs its own
replacement: at minimum constant, linear, and `a + c·b^k`, with every result
checked by expansion.

**Every index starts at 1** because it is hard-coded (`{varName, 1, …}`), and
rolling only ever moves the upper limit.

**Index names.** Each name is the first one not in use, and passes run in order
of increasing body length. So the shortest bodies get the lowest numbers:

- Example 3: `{1, 3}, {1, 4}` (body of 1) is `n$1`; the head block (body of 3)
  is `n$2`; the main block (body of 5) is `n$3`.
- Example 4: the inner `j` block (body of 1) is `n$1`; the outer block is `n$2`.

**Small blocks are made even when they save nothing.** Step 3 accepts any
skeleton that repeats twice, so `{1, 3}, {1, 4}` becomes `€²[{1, 2+n$1}]`, and
two periods with a negative step become `€²[{1,1,2}, {}, {1, 4−n$2}]`.

**Leftovers at the edges** are whatever no match or roll could cover. They go
through steps 1 and 2 like everything else, which is why tails show up as
literals and runs:

| Example | Tail left over | What it is |
|---|---|---|
| 2 | `€²[{29}]` | the start of period k = 28 |
| 3 | `{42, 43}` | the first element of period k = 39 |
| 4 | `{255, 256, 257}, €²²⁰[{257}]` | period k = 8, cut off after 220 of its 257 repeats |

### Answer to the open question (example 3)

Why does example 3's block start at `{4, 5}` when `{3, 4}` with k = 0 would
also fit? Tracing the run shows the order of events:

1. The first generic pass (body of 1) compresses `{1, 3}, {1, 4}`, elements
   10–11, into `€²[{1, 2+n$1}]`.
2. A later pass (body of 5) finds the main block starting at `{4, 5}`.
3. Rolling then tries to move left. The item it would roll out is a single
   element, `{1, 4}`, but the item to its left is now `€²[{1, 2+n$1}]`, which
   expands to two elements. The roll can't take only part of an item, so the
   expansion no longer matches and rolling stops.

So the extension was blocked by the greedy earlier step: the small block
`n$1` sits across the boundary of the period. This is a side effect of the
order the steps run in, not a rule about where periods start.

### Quirks worth knowing before porting

- **The value 1 is special.** Since 1 is kept in the skeleton, a number that
  happens to be 1 in one period and 2 in the next has different skeletons in
  the two periods. Step 3 alone won't match it, and only rolling can recover
  it.
- **The search is greedy.** The first body length that matches anywhere wins,
  and its blocks are fixed before longer ones are tried. That can block better
  reductions, as in example 3.
- **`If[pos == 0, …]` (line 898)** compares a list with 0, so it never takes
  the early return. It's harmless, because an empty match leaves the list
  unchanged and the loop ends.
- **Integers are read with `Cases[…, _Integer, ∞]` and written back with
  `Position[…, _Integer]`.** These are two separate traversals of the nested
  structure. The expansion check at the end catches any case where they don't
  correspond.

### What a Python reducer needs, revised

1. Runs of one element, then exact runs of longer blocks, re-reducing after
   every change.
2. A skeleton where integers other than 1 become 0, then the shortest
   repeating skeleton stretch, with non-overlapping matches scanned from the
   left.
3. A fitter for each column of integers that stands in for
   `FindSequenceFunction`: constant, linear, and `a + c·b^k` to start with.
4. Rolling: rotate the body, shift the index, absorb items on the left, extend
   the upper limit, and absorb whole periods on the right.
5. First unused index name, index always starting at 1.
6. Check every candidate by expansion before keeping it.

To reproduce the Mathematica output exactly, the Python version should follow
this same order. A version that does better than Mathematica (for example,
not letting a small early block block a larger one, as in example 3) can be
an option layered on top, and these examples serve as the reference for both.


## A new reducer

[`musicic/core/concat.py`](../musicic/core/concat.py) is a rewrite aimed at
compressing more than `ReduceSetList`, not at copying its output.
`concatenate(rows)` returns the tree, its text and a `verified` flag. The
result always expands back to the input exactly; if it ever didn't, the code
falls back to collapsing runs only.

### How it differs from ReduceSetList

1. **Atoms instead of elements.** Rows are first grouped into runs (a row
   repeated n times) and progressions (at least 3 rows with a constant step).
   Both are stored as a start row, a step and a count. A single row has no
   step, and that wildcard is what lets a period with one copy line up with
   periods that have a run.
2. **The skeleton is row lengths only.** The value 1 is not special here.
3. **Every candidate is scored, not taken greedily.** For each body length and
   start position, the search grows the block period by period while every
   column (each entry of the start row and step, and each count) can be fitted
   as a function of k. It then keeps the block that saves the most leaves.
   When two save the same, the one with simpler formulas wins.
4. **Formulas.** The fitter (`fit` in `concat.py`) tries, simplest first:
   constant, linear, `a + c·b^k` (b = 2, 3, 4, 5, 10), quadratic, and
   `a + b·k + c·b^k`. Everything beyond a straight line must also predict a
   point it was not fitted on. A line through only 2 points is accepted only
   when it is a constant or a step of ±1, which rules out lines like
   `59 − 29k` that fit any two numbers.
5. **Extension at the row level, in place of rolling.** The chosen body is
   evaluated at k = 0, −1, … and k = q+1, … against the raw neighbouring rows,
   where a count of 0 or 1 is fine, and at every rotation of the body. This is
   how periods the grouping couldn't line up are absorbed, and how the start
   of a period is chosen.
6. **The rows on either side are reduced again from scratch.** Nothing chosen
   for the main block can block a smaller structure next to it, or the other
   way round. This is the fix for the example 3 problem.

### Checks

- `tests.py` (section 7b) runs all five sets. Each must expand back to its
  input exactly and be no larger than the sizes above.
- A fuzz run of 300 lists (half random, half generated from a random period
  with linear, `k`, `2^k` counts plus noise at both ends) gave no wrong
  output and no output larger than collapsing runs. The slowest list took
  2.2 s. 98 of the 100 generated lists reduced to 12 leaves or fewer. The other 2
  are short (32 and 36 rows) and not yet diagnosed.

### Known limits

- Nesting goes two levels deep: an outer block whose body holds runs and
  progressions. A body that contains a repeating *group* of rows with its own
  index (rather than a single row) is not searched for yet.
- The formulas available are the ones listed above, not everything
  `FindSequenceFunction` can find.
- It takes 3–10 s on these sets. Most of that is the search over body lengths
  up to 64 atoms.
